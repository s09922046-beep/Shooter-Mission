# 可操作預覽頁:讓使用者實際操作後挑方案

## 這個流程解決什麼

動態的東西(特效、動畫、手感)只看靜態截圖會選錯。這個流程的來源專案裡,同一個特效曾經「截圖好看、實玩不好」而重做;也曾因為對照截圖沒有每一幀都畫,問題根本沒出現在圖上。讓決定的人在瀏覽器裡實際操作、同一個場景下即時切換方案,一次就選對的機率高很多。

## 適用前提

- 專案是能在本機瀏覽器直接開啟的網頁(單一 HTML 最省事;多檔案專案要確認複製後相對路徑仍有效)。
- 候選方案能用「覆寫函式、切換參數」的方式疊在現行版上。需要改資料結構或後端的方案不適用,改用分支各做一版。
- 決定權在使用者,而且使用者在場可以開瀏覽器看。
- 自檢需要 Node 18 以上、`playwright` 套件與 Chrome。

## 步驟

1. **先重現問題,找到原因。** 用截圖或量測確認問題真的存在、發生在哪些場景。原因沒找到之前不要設計方案。
2. **設計 3 到 5 個方向。** 每個方向要是真的不同的做法,不是同一做法的參數微調(微調放在控制列的下拉選單)。把先前類似問題的解法直接搬過來,列為其中一案。自己不看好的方案也可以放,但交付時要說明為什麼不看好。
3. **寫 variants.js。** 約定如下,現行做法一律放第 0 個當對照組:
   ```js
   window.__PV={names:['現行','A 外框上層','B 半透明'],mode:0};
   (()=>{const f0=drawFlame;                 // 保留原函式
     window.drawFlame=function(){if(!__PV.mode)return f0();  /* 依 __PV.mode 畫各方案 */ };})();
   ```
   全域名稱用 `__PV` 是因為短名稱容易和專案自己的變數撞名(來源專案就有一個 `PV`,撞名時不會報錯,只是切換無效)。方案程式只改顯示,不要改到判定、數值或存檔。
4. **產生預覽頁。** `node scripts/make-preview.js <來源.html> <variants.js> preview/<名稱>.html [額外控制列.html]`。來源檔不會被改。額外控制列放專案專屬的輔助:跳到要比較的畫面、預設好最能看出差異的狀態、無敵或不扣血、慢動作。使用者不該花力氣「走到」要看的地方。
5. **自檢。** `node scripts/check-preview.js preview/<名稱>.html <截圖前綴> [setup.js]`。它逐一切換方案、收集執行錯誤、各存一張截圖。看截圖確認三件事:問題在「現行」確實看得到、每個方案的畫面確實不同、沒有方案把別的東西弄壞。需要多場景並排比較時,另寫對照圖(列為場景、欄為方案)。
6. **交付。** 告訴使用者檔案的完整路徑與操作方式(F6/F7 切方案、F4 收控制列),用一張表列出每個方案的做法與你的真實看法,明確說出你建議哪一個、每個方案的已知缺點。成本(效能、工作量)有差異時一併說。
7. **定案後。** 把選定的方案正式寫進原始檔(通常要重寫成精簡版,預覽時的全畫面處理改成只處理必要範圍);在專案的決定記錄寫下:選了哪個、沒採用哪些、為什麼;用新舊版對照圖驗證正式版與預覽時選的畫面一致;刪掉預覽專用的程式。

## 驗收方式

- `check-preview.js` 回報全部方案無執行錯誤,且截圖顯示方案之間確有差異。
- 使用者實際開啟並回覆選擇(不是 Claude 代選)。
- 正式版完成後,新舊對照圖與使用者在預覽時看到的選定方案一致,原有的回歸測試照常通過。

## 限制與已知的坑

- **截圖不能代替實際操作。** 截圖只證明「有畫出來」。會動的效果一律請使用者操作後再決定。
- **截圖流程要每一幀都畫。** 粒子、快取這類只在繪製時推進的狀態,若只更新邏輯、最後才畫一幀,效果不會出現在圖上。
- **內嵌或外部圖片是非同步載入。** 第一次截圖前先畫幾幀並等約 0.3 到 0.5 秒,否則會截到缺圖的畫面。
- **預覽頁不提交。** 放在已列入 `.gitignore` 的資料夾(例如 `preview/`),避免未定案的程式混進正式歷史。產生檔案前先確認目標檔名不存在,不要覆蓋使用者留著的舊預覽。
- **預覽版的效能不代表正式版。** 預覽為了快速比較常用整張畫面處理,定案後才最佳化;效能要在正式版另外量。
- **方案數不要多。** 超過 5 個,使用者會難以比較;組合型的選項(例如「A 加 B」)只在兩者都有人想要時才放。
