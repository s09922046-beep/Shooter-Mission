## 二、沒有做成 skill 的項目與原因

- **效能做法**:是知識清單,不是流程;而且適用面只有 Canvas 2D。硬做成 skill 會在不相干的專案被誤觸發。
- **問卷式四回合流程**:四回合的內容(判定稽核、小樣總表)離開本專案就不成立,可通用的只剩「一次問完、附選項與建議」一句話。
- **無頭瀏覽器測試工具**:沒有獨立做 skill。可通用的手法是「新舊版並排對照圖」「同一幀有無該物件各畫一次比像素差」「固定亂數種子」,前兩項已在 `playable-preview` 的自檢與限制中,第三項寫進下方範本。
- **發佈流程**:只有三個指令,寫在 AGENTS.md 即可。

## 四、AGENTS.md 通用範本(新專案複製後改寫專案專屬部分)

```markdown
# <專案名> 工作規則

## 開工流程(每次對話都做)
1. 先讀 `design-decisions.md`,它是唯一的長期記憶與決定記錄;細節才讀 changelog 最後一筆。
2. 核對版本一致:主檔開頭的 VERSION、決定文件的「目前版本」、最新的版本 tag。不一致先告訴使用者,不要開始改。
3. 確認本次只有一個工作項目。使用者沒指定就先問。
4. 檢查文件有無過時或重複之處;有刪就告訴使用者刪了什麼。

## 範圍
- 本階段只做 <範圍>。範圍外的改動必須是使用者在對話中明確授權,且已記錄在決定文件;沒有記錄就不算授權。
- 範圍外的想法只在對話最後列出,不要動手。
- 自己的記憶與專案檔案矛盾時,以專案檔案為準,並提醒使用者。

## 需要使用者決定的事
- 有多種做法或需要美術判斷時,先問,不自行決定。
- 一次問完:所有問題放在同一份問卷,每題附選項與建議,讓使用者以「1A 2B」一次回覆。
- 會動的效果用可操作預覽頁讓使用者實際操作後再選(skill:playable-preview),不要只給截圖。

## 完成一個工作項目時,同一輪做完
1. 主檔修改完成,更新 VERSION。
2. 決定文件:更新目前版本、最新一筆、該版新增的決定(只改對應那一行),寫下沒採用的方案與原因。
3. changelog 末端新增一筆:決策過程、實作、驗證、效能、對範圍外是否有改動的聲明。
4. 提交並推送,提交訊息開頭寫版本號;打 tag。

## 測試
- 提交前用 `git diff` 核對只動到預期位置,沒有混入預覽或暫存檔。
- 「沒有執行錯誤」不等於「有畫出來」。有畫面的功能要有一項檢查實際看輸出(同一幀有無該物件各畫一次,比像素差)。
- 新行為要驗證時,在測試工具加子指令,不寫用完就丟的腳本。
- 比較新舊版用固定亂數種子與 `git show <版本>:<檔案>` 取出舊版並排。
- 效能數字在開發機沙盒只作新舊相對比較;目標機器的量測由使用者執行,需要時提出測試範圍。

## Git
- 工作在 `dev`,`main` 只在使用者明確說「發佈」時更新(確認 `main` 是 `dev` 的祖先後 `git push origin dev:main`,不改寫歷史),之後連線確認線上內容已更新。
- 不 force push,不刪遠端分支。
- 未定案的預覽不提交(`preview/` 列入 .gitignore);覆蓋 `preview/` 裡的檔案前先確認不是使用者留著的。
- 決定文件、本檔、測試工具、素材原檔都納入版控。
```
